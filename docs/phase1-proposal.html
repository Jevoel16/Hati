Section B: Project Concept & Motivation

Working title

Hati (Filipino for "to split"): a shared expense splitter with live balances.

Core functionality

  • Accounts. Users sign in with Google or GitHub, which confirms their email, then choose a username and password.
  • Groups. A user creates a group (for example a boarding house, a project team or a trip) and invites others with a code or link. Each group has an admin and members.
  • Expenses. Any member records an expense with the payer, amount, category, date and how it is split: equally, by exact amounts or by percentage.
  • Balances. The system computes each member's net balance and reduces the group's debts to the fewest payments needed to settle.
  • Settlements. Members record a payment made to another member, and the balances adjust.
  • Live monitoring. Balances and an activity feed update in real time for everyone viewing the group, with no page refresh, through WebSockets.
  • Summaries. Each group has a spending summary by category and by month.

Hati keeps records only. It does not process or hold real money.

Problem statement

Students who share costs, such as housemates paying rent, utilities and groceries, project groups buying materials, or friends splitting a trip, usually track them in group chats, notes or memory. Entries get buried, arithmetic is done by hand and each person keeps a different version of the total. The result is forgotten debts, wrong amounts and uncomfortable disputes among people who live or work together. There is no single, current record that everyone in the group can see and trust.

Why this project?

  • It solves a problem the team and its classmates have. The intended users are easy to reach for feedback and testing.
  • It is a live data monitoring system built entirely in software. Every member of a group watches the same balances change as expenses are added, with no hardware or sensors required.
  • It exercises the full course. The system needs a RESTful API, server middleware, JWT authentication, a WebSocket server, a relational database with strict data integrity, containerized deployment and a CI/CD pipeline.
  • The scope fits four people and one semester. The core (groups, expenses, balances, live updates) is small enough to finish and test properly, and summaries can grow if time allows.
  • Correctness matters. Money calculations must be exact, which gives the team real practice in validation, database constraints and automated testing.

Section C: Technical & Non-Technical Specifications

Technical specifications

LayerChoiceDetails
Front-EndReact (built with Vite)Single-page application with React Router; plain CSS with shared design tokens; the browser's native WebSocket API for live updates.
Back-EndNode.js with ExpressRESTful API; middleware for input validation, rate limiting and error handling; Google and GitHub OAuth sign-in; a signed JWT in an httpOnly, SameSite cookie that names a session row in the database, so any sign-in can be revoked; passwords hashed with bcrypt; a WebSocket server (ws) that pushes balance and activity events to everyone viewing a group.
DatabaseMySQL 8 locally, TiDB Cloud when deployed (relational, MySQL-compatible)Normalized schema with foreign keys, ENUM status columns and check constraints, with the same rules also enforced in code; amounts stored as whole centavos to avoid rounding errors; parameterized queries only, through mysql2.
DeploymentDocker, GitHub Actions, VercelSeparate containers for the database, API and web client, run together with Docker Compose in development; GitHub Actions runs lint, type checks, tests (against a TiDB database) and the build on every push; in production, one Vercel project serves the React site and runs the REST API and WebSocket in a single function, deployed on every push to main; TiDB Cloud Serverless database; HTTPS throughout.

Non-technical specifications

Target audience

  • College students sharing a boarding house, dormitory or apartment.
  • Project, thesis and organization groups that buy materials together.
  • Friend groups splitting trips, meals and events.

Core value proposition

One live, shared and accurate record of who owes whom, which every member sees update the moment an expense is added, and which shows the fewest payments needed to settle up.

UI/UX accessibility goals

  • Text and controls meet WCAG 2.1 AA colour contrast.
  • Every action can be done with the keyboard alone, with a visible focus indicator.
  • Semantic HTML, labelled form fields and clear error messages that work with screen readers.
  • Mobile-first layout that works down to a 360px-wide screen, since most users will be on phones.
  • Light and dark modes, and reduced motion for users who request it.
  • Amounts owed and amounts due are shown with words and signs, never by colour alone.
  • Adding an expense takes one short form, so the app is quicker than typing into a group chat.

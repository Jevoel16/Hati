Section B: Project Concept & Motivation

B.1 Working Title

Hati (Filipino for "to split"): a shared expense splitter with live balances.

B.2 Core Functionality

  • Accounts. Users sign in with Google or GitHub, then choose a username and password.
  • Groups. A user creates a group (for example a boarding house, a project team or a trip) and invites others with a code, a link or a QR code to scan. Each group has an admin and members.
  • Expenses. Any member records an expense with the payer, amount, category, date and how it is split: equally, by exact amounts or by percentage.
  • Balances. The system computes each member's net balance and reduces the group's debts to the fewest payments needed to settle.
  • Settlements. Members record a payment made to another member, and the balances adjust.
  • Payment QRs. Members save up to five payment QRs (GCash, Maya or a bank), and whoever owes them scans one with the exact amount filled in. Payment QRs work in peso groups.
  • Currency. Each group picks its currency when it is created (Philippine peso by default), and every amount in the group uses it.
  • Live monitoring. Balances and an activity feed update in real time for everyone viewing the group, with no page refresh, through WebSockets.
  • Summaries. Each group has a spending summary by category and by month, and any month can be downloaded as a CSV expense report.
  • Guided tour. A short step-by-step tour shows first-time users how to create a group, add an expense and settle up. It can be skipped or replayed.

Hati keeps records only. It does not process or hold real money.

B.3 Problem Statement

Students who share costs, such as housemates paying rent, utilities and groceries, project groups buying materials, or friends splitting a trip, usually track them in group chats, notes or memory. Entries get buried, arithmetic is done by hand and each person keeps a different version of the total. The result is forgotten debts, wrong amounts and uncomfortable disputes among people who live or work together. There is no single, current record that everyone in the group can see and trust.

B.4 Why This Project?

  • It solves a problem the team and its classmates have. The intended users are easy to reach for feedback and testing.
  • It is a live data monitoring system built entirely in software. Every member of a group watches the same balances change as expenses are added, with no hardware or sensors required.
  • It exercises the full course. The system needs a RESTful API, server middleware, JWT authentication, a WebSocket server, a relational database with strict data integrity, containerized deployment and a CI/CD pipeline.
  • The scope fits four people and one semester. The core (groups, expenses, balances, live updates) is small enough to finish and test properly, and summaries can grow if time allows.
  • Correctness matters. Money calculations must be exact, which gives the team real practice in validation, database constraints and automated testing.

Section C: Technical & Non-Technical Specifications

C.1 Technical Specifications

C.1.1 Front-End Framework

React, built with Vite and written in TypeScript.

  • Single-page application with React Router, plus a static landing page.
  • Plain CSS with shared design tokens, and light and dark themes.
  • The browser's native WebSocket API for live updates.

C.1.2 Back-End Framework

Node.js with Express, written in TypeScript.

  • RESTful API with middleware for input validation, rate limiting and error handling.
  • Google and GitHub OAuth sign-in, followed by a username and a password hashed with bcrypt.
  • A signed JWT in an httpOnly, SameSite cookie that names a session row in the database, so any sign-in can be revoked.
  • A WebSocket server (ws) that pushes balance and activity events to everyone viewing a group.

C.1.3 Database Schema Choice

A relational database: MySQL 8 locally and TiDB Cloud (MySQL-compatible) when deployed. Hati's data is linked records (groups, members, expenses, shares and payments) whose totals must always agree, so foreign keys and transactions matter more than a flexible document format.

  • Amounts are stored as integers in the currency's smallest unit (centavos for pesos) to avoid rounding errors.
  • Statuses are ENUM columns. Check constraints guard the data, and the same rules are enforced in code, since TiDB may not enforce CHECK.
  • Parameterized queries only, through mysql2, with versioned migration files.
  • sessions holds one row per signed-in device; deleting the row signs that device out.
  • group_events is a short-lived outbox: each write adds a row in its transaction, and the server checks it every second to push new rows to that group's WebSockets.
  • rate_limits counts requests per client and time window.

C.1.4 Deployment Plan

  • Development: Docker Compose runs the database, API and web client in separate containers; the app also runs against a local MySQL 8 database.
  • Continuous integration: GitHub Actions runs lint, type checks, tests (against a TiDB database) and the build on every push.
  • Production: one Vercel project serves the React site and runs the REST API and WebSocket in a single function, deployed automatically on every push to main.
  • Database: TiDB Cloud Serverless.
  • Security: HTTPS throughout, with a strict content security policy.

C.2 Non-Technical Specifications

C.2.1 Target Audience

  • College students sharing a boarding house, dormitory or apartment.
  • Project, thesis and organization groups that buy materials together.
  • Friend groups splitting trips, meals and events.

C.2.2 Core Value Proposition

One live, shared and accurate record of who owes whom, which every member sees update the moment an expense is added, and which shows the fewest payments needed to settle up.

C.2.3 UI/UX Accessibility Goals

  • Text and controls meet WCAG 2.1 AA colour contrast.
  • Every action can be done with the keyboard alone, with a visible focus indicator.
  • Semantic HTML, labelled form fields and clear error messages that work with screen readers.
  • Mobile-first layout that works down to a 360px-wide screen, since most users will be on phones.
  • Light and dark modes, and reduced motion for users who request it.
  • Amounts owed and amounts due are shown with words and signs, never by colour alone.
  • A skippable guided tour introduces each screen, and it works with the keyboard and screen readers.
  • Adding an expense takes one short form, so the app is quicker than typing into a group chat.
